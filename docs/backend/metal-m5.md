本项目优化 llama.cpp 的 Metal 后端在 Apple M5 上的性能，目标是让各种模型（稠密、MoE、不同注意力结构）和各种量化格式都基本达到这台机器的硬件上限。范围包括提示处理（预填充）、解码、投机解码（MTP / DFlash）、并发、短提示、启动和多轮对话缓存。全部改动基于上游 `master` 的 `1268edac5`（b11707，2026-10-17），共 20 个代码提交，每项改动一个提交，各自可以单独关闭。前 15 个面向测试模型用到的 F16 KV 缓存与常见权重格式；后 5 个把同样的内核扩展到 BF16 KV 缓存、量化 KV 缓存、BF16 权重、MLA 的头尺寸，以及上游 Metal 后端原本不支持的 NVFP4 / TQ1_0 两种权重格式（第 6.4 节）。

## 1. 为什么做

在 M5 Max 上，原版 llama.cpp 的 Metal 后端处理提示的速度只有 oMLX 的约 55-70%（例如 Qwen3.8-27B 8k 提示 653 对 1187 t/s），MoE 模型和长上下文下差距更大。实际使用中还有几处明显的损失：投机解码每一步要验证几个 token，这一步比单 token 慢很多；App 默认的 4 路并发，合计吞吐远低于单路的 4 倍；追问、新一轮对话这类短提示落在一段很慢的批次大小上；App 启动后要 3 秒多才出第一个 token，并占用约 21 GB 内存；在界面里关闭思考会让整段对话被重新处理。

M5 这一代在每个 GPU 核心里加入了矩阵单元（NAX，通过 Metal tensor API / MetalPerformancePrimitives 的 `matmul2d` 调用）。MLX 用寄存器常驻的内核驱动它；上游 llama.cpp 只通过一个用 threadgroup 内存分块、以 f32 激活为输入的内核来用它，大部分新增算力没有用上。

目标：
- 尽可能接近 M5 Max 的硬件上限，在可公平对比的项目上追平或超过 oMLX；
- 合适的地方借鉴 MLX、oMLX 等 Apple Silicon 引擎的做法，也做出它们都没有的优化；
- 讲究性价比：单项最终增幅低于 1.5%（噪声级）、却需要复杂验证或大量改动的方案不做；保留的方案用必要最小的改动实现；收益大时允许较大的重构；
- 只改 Metal 后端（以及外面必要的最少几处），每项改动都可开关、都经过数值验证；
- 覆盖 Metal 矩阵乘内核支持的全部权重格式，以及稠密、MoE 和各种注意力结构，而不只是测试模型用到的情形。

在本机实测的硬件上限（M5 Max，40 核 GPU，128 GB）：

| | 数值 |
|---|---|
| 内存带宽（Apple 规格） | 614 GB/s |
| 实测可持续带宽 | 530-580 GB/s（随测试内核、传输大小和运行状态浮动） |
| NAX f16 mat-mat，可达 | ~60 TFLOP/s（MLX 稠密 f16 gemm 59-60；下文 A3 为 59.7） |
| NAX int8 mat-mat | ~2.1x f16（同样的寄存器常驻内核结构） |

解码受带宽限制：例如 Qwen3.8-27B Q5_K_M 每个 token 读 18.34 GB 权重，Llama-3.1-8B Q4_K_M 读约 4.6 GB；本分支单 token 解码中矩阵乘部分的读取速度为 517-540 GB/s，已在可持续带宽范围内，剩下的是注意力和小算子（第 11 节）。

## 3. 效果

对 oMLX 的公平原则：凡是本分支的改动在 oMLX 里有同类选项的，oMLX 也打开：其 INT8 激活预填充（与 I8 对应）开启。其余改动（NAX 注意力、NAX mat-mat、GDN 内核、激活融合）对应的是 MLX/oMLX 一直在用、没有开关的路径。KV 缓存量化两边都关闭；不开投机解码的对比两边都关，开的对比两边都开。oMLX 的设置在测量前读出、测量后恢复并核对。oMLX 在单独的时间段测量，所以对 oMLX 的比值是跨时间段的。

端到端：1,877 / 8,100 / 31,873 token 的提示（下文写作 2k / 8k / 30k；oMLX 的分词不同，token 数略有出入），生成 128 / 256 / 256 token。本分支与上游正序、反序各一轮取均值。llama-bench：`-fa 1`，预填充与每步耗时用 `-ub 2048`（llama-bench 默认的 512 低于 NAX mat-mat 1024 行的门槛，App 与服务器默认 2048），正反序各一轮。并发：App 的布局 `-np 4 -kvu`，300 词提示，生成 128 / 256 token，合计解码 t/s。

### 3.5 小结

- 预填充：稠密模型 llama-bench `pp2048` 为上游的 1.5-2.0 倍（Qwen 1.75 倍，Llama 三种格式在 8k / 32k 深度 1.9-2.0 倍），MoE 模型 1.1-1.9 倍（gemma 1.14-1.33 倍，gpt-oss 1.26-1.86 倍，深度越大越多）。服务器端到端 8k 提示：Qwen 1.69 倍，Llama 1.70 倍，gpt-oss 1.32 倍，gemma 1.13 倍。
- 解码：短上下文与上游持平（0.99-1.01 倍），长上下文更快：30k 时 Qwen +4%、Llama +5%、gpt-oss +17%、gemma +21%（H3 的 GQA 打包注意力）。
- 投机解码与小批量：一步 16-64 个 token 是上游的 1.0-2.7 倍（H4 / M1）；30k 上 Qwen 的 MTP 40.8 对 32.9 t/s，gemma 的 DFlash 109.8 对 76.6 t/s。
- 并发（App 的 4 路布局）：2-4 路合计 1.0-1.22 倍，4 路投机解码 Qwen 1.36 倍、gemma 1.18 倍。gemma 单路投机解码 0.97 倍是这一个提示上的接受率差异（0.206 对关闭 A2 门槛时 0.227，提示的数值略有不同导致生成的文本不同），不是内核变慢：这一步里被门槛影响的只有 342 token 的提示预填充。
- 与 oMLX：预填充 Qwen 持平、Llama 快 26%，gemma / gpt-oss 慢 3-9%；解码 gemma 快 8%、gpt-oss 快 26%，Qwen / Llama 慢 2-7%（Llama 部分来自 oMLX 的 4-bit 文件小 8%）；Qwen 的 MTP 在 8k 上 oMLX 明显更快（见第 11 节）。
- 启动与内存：Qwen 就绪 1.9 对 2.7 s，常驻内存 3.3 对约 21 GB；关闭思考后不再重新处理整段对话。
- 精度：除 I8 外的改动与上游一致到参照量级；I8 在 gemma 上有可见代价，可单独关闭（第 10 节）。
- 扩展（第 6.4 节）：BF16 KV 缓存的预填充比上游的 BF16 tensor 内核快（Llama pp2048 @32k 1.32 倍，gpt-oss 1.55 倍），但 gemma 预填充慢约 5%、Llama 32k 解码慢 14%，尚未处理；BF16 权重的预填充 1.14-1.16 倍；MLA（GLM-4.7-Flash）预填充 @32k 1.25 倍；量化 KV 缓存（q8_0 / q4_0）的长上下文解码 gemma 1.28-1.33 倍、gpt-oss 1.07-1.11 倍，一步 2-4 个 token 时最多 2.0 倍；NVFP4 / TQ1_0 的矩阵乘从 CPU 移到 GPU。

## 4. 方法

- **先算差距账。** 动手之前，先用调试开关逐类跳过算子，测出每类算子的耗时并与硬件上限比较；只处理上限明显高于 1.5% 的部分。新模型也一样：例如 gpt-oss 预填充 69% 的时间在 MoE 专家矩阵乘（MUL_MAT_ID）上，这一部分只跑到稠密路径一半的算力，M1 / M2 由此而来。
- **先筛选，再确认。** 受算力限制的候选先在合成权重上做内核级 A/B（同一进程内交错），增幅超过 1.5% 且多轮方向一致才进入真实模型测量。保留的方案全部在满功率（`powermode 0`）下确认，本文所有数字都是满功率数据。
- **交错测量。** 不同场次之间绝对数值会随发热状态漂移 5-15%。每次对比都在同一场次里按正序再反序运行各配置，只比较同一场次内的比值。测试之间间隔 2 分钟；漂移过大的测试段作废重测。
- **按留一法取舍。** 一项改动看的是它在最终组合中的贡献（全部开启减去这一项），而不只是单独开启时的效果。
- **按格式、按形状逐一验证。** 矩阵乘类改动对每一种权重格式分别在合成权重上做内核级 A/B（稠密：17408x5120 与 5120x17408；MoE：gemma-4 与 gpt-oss 的专家形状），只对确实更快的格式和行数范围开启；同时比对两条路径的输出校验和。
- **按模型结构验证。** 注意力类改动在四种结构上测：每个 KV 头对应 4 / 6 / 8 个 query 头，head size 64 / 128 / 256 / 512，有无 sinks。某个结构上变慢的情形用门槛排除（例如 H3 对每 KV 头 4 个 query 头的单 token 解码）。
- **精度把关。** 每个模型都以上游的完整 logits 为基准测 KL 散度（逐 token 配对比较，比困惑度灵敏得多），并以上游自身 `-fa on` 与 `-fa off` 之间的差作为"正常数值差异"的参照；有损的改动要么改进到参照量级附近，要么写明代价并可单独关闭（见第 10 节）。
- **固定提示。** 投机解码的速度取决于生成文本接受了多少草稿；对单项改动的端到端对比使用固定提示，并确认输出文本相同后再比较耗时。
- **上游核查。** 每次都在上游最新 `master` 上重建并重新测量；本文的上游数据测自 `318a471a6`（b11628）；此后到 `620d2225c` 的上游提交中，涉及 Metal 后端的只有一个：tensor API flash attention 内核增加 BF16 版本并移到 `kernels/fa_tensor.metal`（#30491）。本文的模型都用 F16 KV 缓存，F16 版本的内核只是改成按类型的模板，测量的路径不变；本分支的 NAX 注意力内核随之移到同一文件（BF16 KV 缓存后来也改走 NAX 内核，即 A1-BF16）。分支随后变基到 `1268edac5`（b11707）：这 38 个上游提交都不涉及 Metal 后端，变基没有冲突，每个提交的改动除行号外不变，所以不需要删减。上游还有两个思路相近、尚未合并的 PR：#30645（tensor API 的 GQA 小批量解码注意力，F16 缓存、head size 128/256、1-4 个 token，与 H3 重叠）和 #30047（MUL_MAT_ID 的 few-row MMA，与 M1 / M2 同一段批次）；它们合并后要重新核对重叠的部分。#30645 会跳过整块被掩码的 KV 块，H3 还没有这一点，值得借鉴。

| A4 | +1.8% | +3.4% |

内核级（同进程交错 A/B，2048 行）：
- A1：flash attention q2048 x kv8192 21.6 -> 11.8 ms，kv32768 100 -> 55 ms（对比上游 tensor-API 内核）。

## 8. 保留项的实现

**代码结构**。各项 NAX 内核共用 `kernels/common.h` 里的两个原语：`nax_coord`（片段的 lane 布局）和 `nax_mma<C, A, B, TB>`（一次 16x32x16 的 `matmul2d`，f16 与 int8 共用）。f16 与 int8 的 NAX mat-mat 是同一个内核模板 `kernel_mul_mm_nax_impl<T>`，int8 只多出按组折回 scale 的一段（`if constexpr`）；主机端两者共用一个派发函数（分块、swizzle、split-K）。两个 NAX 注意力内核（A1 的预填充、H3 的 GQA 打包）各自保留内联的 KV 块步骤：把它抽成共用函数后 head size 512 的内核慢 1.55 倍（第 9.4 节）。三处反量化实例（dq -> f16、dq -> int8、few-row）由同一个格式列表 `NAX_QTYPES` 生成，新增格式只需加一行（F4 的两种格式就是这样加入的）。不带函数常量的 pipeline 统一用 `ggml_metal_library_get_pipeline_by_name` 按内核名取得。这样整理后前 15 个提交相对上游为 +2950 / -70（整理前 +3315 / -70），数值与整理前逐位相同（KL 散度 0，top-1 100%）。

**A1：NAX flash attention**（`kernels/fa_tensor.metal`，派发在 `ggml-metal-ops.cpp`）。F16 K/V 的预填充注意力把分数、概率和 O 都留在寄存器里（16x32x16 的 `matmul2d` 片段，BQ = 64，BK = 32），结构参照 MLX 的 `steel_attention_nax`；head dim 分给 WN 个 simdgroup（head size 64 和 128 为 1 个，256 为 2 个，512 为 4 个），各自的部分分数按固定顺序经 threadgroup 内存相加。每个块的掩码标志提前一块预取：否则跳过全掩码块的那个分支每次迭代都要等设备内存读取（单这一点端到端 +4-8%）。attention sinks 只改变 softmax 的分母，所以在归一化前把 sink 并入最后的 M / S，并把它对 O 的缩放并进归一化系数。遇到 ALiBi 和 softcap 时回退到原有的 tensor 内核。

**A2：f16 激活**（`kernels/mul_mm.metal`、`ggml-metal-ops.cpp`、`ggml-metal.cpp`）。tensor `mul_mm` 内核用 half 激活比用 f32 快约 1.25 倍，所以先把 f32 激活转换（饱和到 +/-65504）到一个额外的缓冲区。只用于稠密 mat-mat（MoE 版本见第 9 节）。

**A3：NAX mat-mat**（`kernels/mul_mm.metal`、`ggml-metal-impl.h`、`ggml-metal-ops.cpp`）。批次至少 1024 行时（`GGML_METAL_MM_NAX_MIN_ROWS`，测试用参数），每个 mat-mat 先把权重经该格式的反量化函数转成 f16 一次，然后在一个不用 threadgroup 内存的内核上做乘法：操作数直接载入片段，每个 64x128 tile 由 2x4 个 simdgroup 计算，threadgroup 做 swizzle，每 256 K 一次 barrier。禁止 K 循环展开是它变快的关键（0% -> 15%）。当 K >= 3*max(M, N) 时，K 被切成 4096 宽的分段依次派发、累加到 dst，使操作数切片留在缓存里（MLX 对长 K 也这样做）。

**A4：GDN 每行 4 个 lane**（`kernels/gated_delta_net.metal`、`ggml-metal-ops.cpp`）。原来每个状态行 32 个 lane，递推受指令数限制（每个 token 两次 5 步归约）。改为每行 4 个 lane（状态大小 256 时为 8 个，否则每个 lane 需要 64 个寄存器）后，每个 lane 保存 32 个状态值，归约只需 2 步（8 lane：1.87 倍，4 lane：1.98 倍）。其他形状、非标量 gate 和未对齐的输入仍走原有内核。

**I8：int8 mat-mat**（`kernels/mul_mm.metal`：`kernel_mul_mm_q8a_f32`、`kernel_mul_mm_dq_<type>_i8`、`kernel_mul_mm_nax_i8`）。激活和反量化后的权重都量化为对称 int8，每（行，128 列）一个 scale；量化前对每组 128 个值做一次不归一化的 Walsh-Hadamard 变换（`i8_wht128`，32 个 lane 各持 4 个值，组内 2 级加减 + 5 级 `simd_shuffle_xor`），两边用同一个变换，点积不变（1/128 折进激活的 scale），而离群值被摊到整组，scale 不再被少数大值撑大。`matmul2d<int8, int8, int32>` 累加 128 宽的一组 K，然后折回到 f32 累加器（`c += s_a*s_w*ci`）。tile 结构和 split-K 与 A3 相同；它复用 A3 预留的缓冲区，不需要额外内存。每 32 列一个 scale 精度也更好，但折回次数多 4 倍，Qwen pp2048 慢 25%，所以保持 128 列、用变换补精度：KL 散度 Qwen 0.0023 -> 0.0007、Llama 0.0009 -> 0.0004、gemma 0.112 -> 0.067，速度代价 0-2%。这与 CUDA MMQ 路径的 q8_1 激活以及 oMLX 的 oq_a8 属于同一类有损捷径（精度见第 10 节）。

**A5：SWIGLU -> down 投影**（`ggml-metal-fusion.cpp`、`kernels/unary.metal`）。当 SWIGLU 的输出送入一个 NAX mat-mat 时，GLU 内核直接写出该 mat-mat 所需的 f16 或 int8 激活（含 scale）；f32 的 GLU 输出和单独的转换那一遍都省掉了。结果与不融合的路径逐位相同。

**S1：关闭思考时保留对话缓存**（`tools/ui`）。界面的思考档位 低 / 中 / 高 原本就以 `thinking_budget_tokens` 发送，切换不会打断缓存；只有"关闭"发送 `chat_template_kwargs.enable_thinking=false`，Qwen3.8 的模板会因此去掉系统部分开头的一段说明，整段对话从第 5 个 token 左右起被重新处理。现在"关闭"改为发送 `thinking_budget_tokens: 0`，输出与模板的空思考块相同，提示前缀不变。新增设置"关闭思考时保留对话缓存"（设置 -> 开发者，默认开启）。

**S2-a：加载时不清零**（`ggml-metal-device.cpp`、`common/common.cpp`）。Metal 的共享缓冲区来自 `vm_allocate`，本来就是零，但 KV 缓存在分配后清零一次、预热后又清零一次，触碰并提交了每个页面（262k 上下文时 KV 约 16 GiB、递推状态 2.4 GiB）。Metal 端记录缓冲区自分配以来是否被触碰过，未触碰时跳过清零；`common` 端在预热后只重置 KV 单元，不擦除数据。

**K3：2-3 行的跨行 mat-vec**（`kernels/mul_mv.metal`）。与单行 mat-vec 相同的 lane 布局，但一个块的量化值和 scale 只解包一次，与 2-3 行激活分别做点积；解包后的值用 half 保存以限制寄存器用量。q4_K 用于 2-3 行，q5_K 用于 2 行。

**S2-c：首次驻留请求放到后台**（`ggml-metal-device.cpp`）。驻留集的第一次 `requestResidency` 会为 GPU 映射每个页面，262k 上下文的 KV 约需 0.4 s。对自分配以来未被触碰的共享缓冲区，这个请求放到后台队列执行，完成后驻留集再加入保活集合；释放缓冲区时会等待它。

**A2 门槛**（`ggml-metal-ops.cpp`）。A2 在 tensor mul_mm 之前把 f32 激活转为 f16，每次 mul_mm 多一次派发和前后两个 barrier，是固定成本；128 行以下这部分成本大于 half 激活省下的时间；128-512 行时，计算量小的矩阵乘（K/V 投影、递推状态的小投影）也是如此（gpt-oss pp128 -7%，Llama Q8_0 -10%）。现在 128 行且单次矩阵乘 4 GFLOP 起才转换（NAX mat-mat 只吃 f16，照旧转换），额外缓冲区也按同一条件预留。门槛扫过 2 / 4 / 8 / 16 GFLOP：4 是唯一在四个模型的 pp128 / 256 / 512 上都不变慢的取值。

**H3：GQA 打包的 NAX 注意力**（`kernels/fa_tensor.metal`：`kernel_flash_attn_ext_nax_gqa`；`ggml-metal-ops.cpp`）。解码和投机解码验证时，vec 内核对每个 query 头读一遍 K/V。新内核把共享一个 KV 头的 G 个 query 头和 ne01 个 token 打包成一个 NAX tile 的行（p = g*ne01 + i），每个 K/V 块只读一次；KV 范围切成 32 份交给 32 个 threadgroup，结果写成 vec 内核的临时缓冲区格式，由现有的 `kernel_flash_attn_ext_vec_reduce` 合并；第一个 threadgroup 同时把 sink 并入它的部分结果（与 vec 内核的做法相同）。最多 16 个打包行用一组 simdgroup，最多 32 行用两组。条件：head size 64-512、F16 K/V、有掩码、没有 ALiBi / softcap、每个 KV 头至少 2 个 query 头；打包后只有不到 5 行（每 KV 头 4 个 query 头的单 token 解码）且 KV 短于 16k 时，tile 的大部分是空行，保持 vec 内核。

**H4：2-64 行的 NAX few-row mat-mat**（`kernels/mul_mm.metal`：`kernel_mul_mv_nax_f32`；`ggml-metal-common.cpp`、`ggml-metal-ops.cpp`）。src1 的行是 16x32x16 matmul2d 的 M = 16 行（一次一个或两个 16 行 tile，更多的行沿网格的第二维分成多遍），32 个权重行是它的 N；每个 lane 通过该格式的反量化函数把 16 个权重直接解到 half 片段里，不用 threadgroup 内存；4 个 simdgroup 切分 K，最后在 threadgroup 内存里求和。为了让每个 lane 一次解出一个完整的 16 权重组（反量化函数的单位），K 在每个 64 权重的块内做了排列，src0 与 src1 用同一个排列。q5_K 另有一个用 16 字节加载和位运算代替逐权重分支的反量化函数。各格式在哪些行数开启由一个函数集中决定（第 7.1 节）。支持与 MUL_MAT + ADD（残差加）融合。

**M1：MoE mat-mat 从 16 个 token 起**（`ggml-metal-common.cpp`）。`ggml_metal_op_mul_mat_id_use_mm` 在有 tensor 单元的设备上把门槛从 32 改为 16；其他设备保持 32。

**M2：MoE mat-mat 每块 64 个条目**（`kernels/mul_mm.metal`：`kernel_mul_mm_id_map0`、`kernel_mul_mm_id`；`ggml-metal-device.cpp`、`ggml-metal-ops.cpp`）。路由预处理把每个专家的条目切成块，主内核对每块把 64 行权重反量化一次并与块内的条目相乘。一个函数常量把块大小从 32 切换到 64（预处理与主内核同时切换）：64 条目的块按 16 行的四分之一块做 `matmul2d`，没有条目的四分之一块跳过；每个线程多装载一行激活；threadgroup 内存从 8 KB 增加到 16 KB。只在有 tensor 单元的设备上、专家平均至少 128 个条目时使用。

**A1-BF16：BF16 KV 缓存**（`kernels/fa_tensor.metal`、`ggml-metal-ops.cpp`）。A1 与 H3 的内核按 K/V 的元素类型做模板：BF16 缓存原样读入，每个元素在寄存器里转成 f16（饱和到 f16 的范围），MMA 里的 Q、K、V、P 仍是 f16。此前 BF16 缓存总是走上游的 tensor 内核。

**A3-BF16：BF16 权重**（`kernels/mul_mm.metal`、`ggml-metal-ops.cpp`）。1024 行起，BF16 权重与其他格式一样，在每个 mat-mat 里先转成 f16 一次（放在量化权重反量化所用的同一个额外缓冲区），再与 f16 激活相乘；不走 int8 路径。1024 行以下保持上游的 f32 激活路径。

**A1-MLA：MLA 的头尺寸**（`kernels/fa_tensor.metal`、`ggml-metal-ops.cpp`）。预填充内核把 K 与 V 的 head dim 分开切分，从而覆盖 DeepSeek / GLM / Kimi 一类模型的 192/128，以及 V 是 K 视图的 576/512（head dim 分给 1 与 4 个 simdgroup）。H3 仍只用于 K、V 头尺寸相同的情形。

**F4：NVFP4 与 TQ1_0 权重**（`kernels/dequantize.h`、`kernels/mul_mv.metal`、`kernels/mul_mm.metal`、`ggml-metal-device.cpp` 等 11 个文件）。两种格式现在走其他格式的全部 Metal 路径：mat-vec（各一个专用内核；NVFP4 另有 2-5 行的内核）、few-row MMA、mat-mat、MoE mat-mat，以及 M5 上经 `NAX_QTYPES` 的 NAX 路径（A3、I8、H4）。NVFP4 在内核里解码 UE4M3 子块 scale（与 CPU 一样把 NaN 编码 0x7F 解为 0），配 mxfp4 的 E2M1 表；TQ1_0 按 CPU 参考实现取出三进制位。

**H3-Q：量化 KV 缓存**（`kernels/fa_tensor.metal`、`ggml-metal-device.cpp`、`ggml-metal-ops.cpp`）。H3 的内核按缓存的块类型实例化（q4_0 / q4_1 / q5_0 / q5_1 / q8_0 / iq4_nl），按字节寻址每一行，每次载入用已有的 `dequantize_*_t4` 在寄存器里解出 4 个值；内核名带上缓存类型。打包后不超过 4 行时，任何长度都是 vec 内核更快，保持 vec 内核；F16 / BF16 的条件不变。批次更大时上游会先把量化缓存转成 F16 再走其他内核，这部分不变。

## 11. 剩余差距

1. **MoE 预填充。** gpt-oss 8k / 30k 提示比 oMLX 慢 6% / 9%，gemma 慢 3% / 5%。M2 之前的耗时分解中，gpt-oss 预填充约 69% 的时间在 MUL_MAT_ID 上，约 26 TFLOP/s，而稠密的 NAX mat-mat 约 52 TFLOP/s；M2 之后 gpt-oss 预填充快了 24-37%，但按专家分块的 mat-mat 仍明显低于稠密路径。下一步是把 A3 那样寄存器常驻的 NAX 内核用到按专家分块的 mat-mat 上（H5 那种 few-row 方案在大批量下更慢，见第 9 节）。
2. **Qwen 的 MTP。** 8k 时 oMLX 的 MTP 解码 57.5 t/s，本分支 42.7（30k 时 43.7 对 40.8）；不用投机解码时两者只差 2-5%，所以差距主要在投机解码这一层（草稿长度、接受率、草稿头本身的开销），本项目只改了 Metal 后端，没有拆分这部分。
3. **解码带宽。** 短上下文的解码已和上游持平，但离带宽上限还有距离：Qwen 2k 解码 26.0 t/s x 19.5 GB ≈ 507 GB/s，Llama Q4_K_M 95 t/s x 4.9 GB ≈ 467 GB/s，即 614 GB/s 标称带宽的 83% / 76%。oMLX 在 Qwen 上快 2-5%。
4. **BF16 KV 缓存的两处变慢。** gemma 预填充比上游的 BF16 tensor 内核慢约 5%；Llama-3.1-8B 32k 解码慢 14%（每 KV 头 4 个 query 头，打包后只有 4 行，与 H3-Q 门槛排除的情形相同，应同样按行数退回 vec 内核）。gemma 的情形要按头尺寸（全局层为 512）再测。目前可以用 `GGML_METAL_FA_NAX_BF16_DISABLE=1` 整体关闭。
5. **中等批次的注意力（进行中，未并入上面的提交列表）。** H3 的 tile 最多 32 个打包行，更多时走 vec 内核（每头少于 20 个 query）或 A1，一步 9-64 个 token、长上下文时离上限最远。正在做的改动把 tile 扩到 64 / 128 行、按行分块派发、每头超过 32 个 query 时减少 KV 的切分份数，并让大批次的量化缓存不再先转 F16。原型的结果（F16 缓存，@32k，新 / 现在，t/s）：Llama-3.1-8B 一步 16 token 515 / 236、32 token 744 / 351，gemma 12 token 469 / 268、32 token 780 / 548，gpt-oss 16 token 631 / 382、32 token 931 / 634；q8_0 缓存 32 token（Llama）500 / 302。打包内核与 A1 的分界仍在测量：Llama 上每头 128 个 query 以内打包更快，256 个时更慢。
6. **离硬件上限最远的算子（屋顶线）。** 以 max(FLOP / 60 TFLOP/s, 字节 / 560 GB/s) 估算理想时间（H3-Q 之前测得）：每头 16 个 query 的注意力只达 0.02-0.15（即上一条），量化 KV 的小批量解码 0.01-0.35（H3-Q 已改善一部分），MLA 576 的解码 0.01-0.14，大批量 MoE mat-mat 0.35-0.6（第 1 条），2-8 与 32-64 行的稠密 mat-vec 约为理想的一半，F16 注意力预填充 0.6-0.84。
7. **I8 的精度。** 在 gemma 上，I8 使 KL 散度约为上游 `-fa on`/`-fa off` 参照的 3 倍（第 10 节）。更细的分组太慢（每 32 列：Qwen -25%），Walsh-Hadamard 变换已收回一部分；彻底解决需要能逐矩阵判断激活分布的办法，目前只能整体关闭。

## 1. Why

On an M5 Max, the Metal backend of stock llama.cpp processed prompts at only about 55-70% of the speed of oMLX (for example Qwen3.8-27B, 8k prompt, 653 vs 1187 t/s), and the gap was larger for MoE models and long contexts. In everyday use there were further clear losses: each speculative decoding step verifies several tokens and was much slower than a single-token step; the app's default of 4 concurrent streams gave far less than 4x the single-stream throughput; short prompts (follow-up questions, new chat turns) fell into a very slow range of batch sizes; the app needed more than 3 s to the first token after start-up and kept about 21 GB resident; and turning thinking off in the interface made the whole conversation be processed again.

The M5 generation adds matrix units to every GPU core (NAX, used through the `matmul2d` of the Metal tensor API / MetalPerformancePrimitives). MLX drives them with register-resident kernels; upstream llama.cpp used them only through a kernel that tiles through threadgroup memory and takes f32 activations, leaving most of the new compute unused.

Goals:
- get as close as possible to the hardware limits of the M5 Max, and match or beat oMLX wherever the comparison is fair;
- borrow from Apple Silicon engines such as MLX and oMLX where it fits, and also do optimizations none of them have;
- cost-effectiveness: no change whose final gain is below 1.5% (noise level) while needing complex validation or a lot of code; the kept changes are implemented with the minimum necessary code; large refactors are allowed for large gains;
- change only the Metal backend (plus the minimum necessary elsewhere); every change is switchable and numerically verified;
- cover every weight format the Metal mat-mul kernels support, and dense, MoE and the various attention structures, not just what the test models use.

Hardware limits measured on this machine (M5 Max, 40-core GPU, 128 GB):

| | Value |
|---|---|
| Memory bandwidth (Apple spec) | 614 GB/s |
| Measured sustainable bandwidth | 530-580 GB/s (varies with kernel, transfer size and state) |
| NAX f16 mat-mat, reachable | ~60 TFLOP/s (MLX dense f16 gemm 59-60; A3 below 59.7) |
| NAX int8 mat-mat | ~2.1x f16 (same register-resident kernel structure) |

Decode is bandwidth bound: for example Qwen3.8-27B Q5_K_M reads 18.34 GB of weights per token, Llama-3.1-8B Q4_K_M about 4.6 GB; in this branch the mat-muls of single-token decode read at 517-540 GB/s, within the sustainable bandwidth, and the rest is attention and small ops (section 11).

### 3.5 Summary

- Prefill: on dense models llama-bench `pp2048` is 1.5-2.0x upstream (Qwen 1.75x, the three Llama formats 1.9-2.0x at 8k / 32k depth), on MoE models 1.1-1.9x (gemma 1.14-1.33x, gpt-oss 1.26-1.86x, more at larger depth). Server end to end with an 8k prompt: Qwen 1.69x, Llama 1.70x, gpt-oss 1.32x, gemma 1.13x.
- Decode: on par with upstream at short context (0.99-1.01x), faster at long context: at 30k Qwen +4%, Llama +5%, gpt-oss +17%, gemma +21% (H3, the GQA-packed attention).
- Speculative decoding and small batches: steps of 16-64 tokens are 1.0-2.7x upstream (H4 / M1); at 30k, Qwen MTP 40.8 vs 32.9 t/s, gemma DFlash 109.8 vs 76.6 t/s.
- Concurrency (the app's 4-slot layout): 2-4 streams 1.0-1.22x in total, 4 speculative streams Qwen 1.36x, gemma 1.18x. The 0.97x for a single speculative gemma stream is a difference in acceptance on this one prompt (0.206 vs 0.227 with the A2 gate off, slightly different prompt numerics lead to different generated text), not a slower kernel: the only work the gate touches there is the 342-token prompt prefill.
- Against oMLX: prefill on par for Qwen, 26% faster for Llama, 3-9% slower for gemma / gpt-oss; decode 8% faster for gemma, 26% for gpt-oss, 2-7% slower for Qwen / Llama (for Llama partly because oMLX's 4-bit file is 8% smaller); Qwen MTP at 8k is clearly faster in oMLX (section 11).
- Start-up and memory: Qwen ready in 1.9 vs 2.7 s, resident memory 3.3 vs about 21 GB; turning thinking off no longer reprocesses the whole conversation.
- Accuracy: the changes other than I8 match upstream to the order of the reference; I8 has a visible cost on gemma and can be switched off alone (section 10).
- Extensions (section 6.4): with a BF16 KV cache, prefill is faster than upstream's BF16 tensor kernel (Llama pp2048 @32k 1.32x, gpt-oss 1.55x), but gemma prefill is about 5% slower and Llama decode at 32k 14% slower, not yet addressed; BF16 weights 1.14-1.16x in prefill; MLA (GLM-4.7-Flash) prefill @32k 1.25x; with quantized KV caches (q8_0 / q4_0) long-context decode is 1.28-1.33x on gemma and 1.07-1.11x on gpt-oss, up to 2.0x for steps of 2-4 tokens; NVFP4 / TQ1_0 mat-muls move from the CPU to the GPU.

## 4. Method

- **Account for the gap first.** Before any change, op classes were skipped one at a time with a debug switch to measure their time and compare it with the hardware limit; only parts with a limit clearly above 1.5% were worked on. Likewise for the new models: for example 69% of the gpt-oss prefill is in the MoE expert mat-muls (MUL_MAT_ID), which ran at half the throughput of the dense path; M1 / M2 came from that.
- **Screen, then confirm.** Compute-bound candidates were first A/B tested at kernel level on synthetic weights (interleaved in one process); only a gain above 1.5% in a consistent direction over several rounds went on to real-model measurements. Every kept change was confirmed at full power (`powermode 0`), and every number in this document is a full-power number.
- **Interleaved measurements.** Absolute values drift 5-15% between sessions with the thermal state. Every comparison runs the configurations forward and then in reverse within one session, and only ratios within a session are compared. Tests are 2 minutes apart; test blocks with too much drift were discarded and repeated.
- **Leave-one-out selection.** A change is judged by its contribution to the final combination (all on minus this one), not only by its effect alone.
- **Per format and per shape.** Mat-mul changes were A/B tested at kernel level for every weight format separately on synthetic weights (dense: 17408x5120 and 5120x17408; MoE: the expert shapes of gemma-4 and gpt-oss), and enabled only for the formats and row ranges that are actually faster; the output checksums of both paths were compared.
- **Per model structure.** Attention changes were measured on four structures: 4 / 6 / 8 query heads per KV head, head sizes 64 / 128 / 256 / 512, with and without sinks. Cases that get slower on some structure are excluded by a threshold (for example H3 for single-token decode with 4 query heads per KV head).
- **Accuracy gate.** For every model the KL divergence to the full upstream logits is measured (paired per token, far more sensitive than perplexity), with the difference between upstream's own `-fa on` and `-fa off` as the reference for an ordinary numerical difference; a lossy change is either brought close to that reference or its cost is stated and it can be switched off on its own (section 10).
- **Fixed prompts.** Speculative decoding speed depends on how many drafts the generated text accepts; end-to-end comparisons of single changes use fixed prompts and compare times only after checking that the output text is identical.
- **Upstream check.** Every round is rebuilt and re-measured on the latest upstream `master`; the upstream numbers in this document were measured at `318a471a6` (b11628); of the upstream commits from there to `620d2225c`, only one touches the Metal backend: a BF16 variant of the tensor API flash attention kernel, with the tensor kernels moved to `kernels/fa_tensor.metal` (#30491). The models here use an F16 KV cache, and the F16 kernel only became a template over the type, so the measured paths are unchanged; this branch's NAX attention kernels moved to the same file (a BF16 KV cache later moved to the NAX kernels too, A1-BF16). The branch was then rebased onto `1268edac5` (b11707): none of those 38 upstream commits touches the Metal backend, the rebase had no conflicts, and every commit's change is the same apart from line numbers, so nothing had to be trimmed. Upstream has two similar PRs that are not merged yet: #30645 (a tensor API GQA attention kernel for small decode batches: F16 cache, head size 128/256, 1-4 tokens; overlaps H3) and #30047 (few-row MMA for MUL_MAT_ID, the same batch range as M1 / M2); the overlap needs another look once they land. #30645 skips KV blocks that are fully masked, which H3 does not do yet and is worth adopting.

## 8. Implementation of the kept changes

**Code structure**. The NAX kernels share two primitives in `kernels/common.h`: `nax_coord` (the lane layout of a fragment) and `nax_mma<C, A, B, TB>` (one 16x32x16 `matmul2d`, used for f16 and int8 alike). The f16 and int8 NAX mat-mat are one kernel template, `kernel_mul_mm_nax_impl<T>`; int8 only adds the per-group scale fold (`if constexpr`), and on the host both share one dispatch function (tiling, swizzle, split-K). The two NAX attention kernels (A1 for prefill, H3 for GQA packing) each keep their KV block step inline: as a shared function it made the head-size-512 kernel 1.55x slower (section 9.4). The three sets of dequantization instances (dq -> f16, dq -> int8, few-row) are generated from one format list, `NAX_QTYPES`, so a new format is a one-line addition (that is how F4 added its two formats). Pipelines without function constants are all obtained by kernel name through `ggml_metal_library_get_pipeline_by_name`. After this cleanup the first 15 commits change +2950 / -70 against upstream (+3315 / -70 before), with results bit-identical to before (KL divergence 0, top-1 100%).

**A1: NAX flash attention** (`kernels/fa_tensor.metal`, dispatch in `ggml-metal-ops.cpp`). Prefill attention with F16 K/V keeps the scores, the probabilities and O in registers (16x32x16 `matmul2d` fragments, BQ = 64, BK = 32), following MLX's `steel_attention_nax`; the head dim is split over WN simdgroups (1 for head sizes 64 and 128, 2 for 256, 4 for 512), whose partial scores are added through threadgroup memory in a fixed order. The mask flag of each block is prefetched one block ahead: otherwise the branch that skips fully-masked blocks waits for a device memory load every iteration (+4-8% end to end from this alone). Attention sinks only change the softmax denominator, so the sink is folded into the final M / S before normalization and its rescale of O into the normalization factor. ALiBi and softcap fall back to the existing tensor kernel.

**A2: f16 activations** (`kernels/mul_mm.metal`, `ggml-metal-ops.cpp`, `ggml-metal.cpp`). The tensor `mul_mm` kernels are about 1.25x faster with half activations than with f32, so the f32 activations are converted first (saturating at +/-65504) into an extra buffer. Dense mat-mat only (for the MoE version see section 9).

**A3: NAX mat-mat** (`kernels/mul_mm.metal`, `ggml-metal-impl.h`, `ggml-metal-ops.cpp`). For batches of at least 1024 rows (`GGML_METAL_MM_NAX_MIN_ROWS`, a test parameter), each mat-mat first dequantizes the weights to f16 once through the dequantize function of the format, then multiplies on a kernel without threadgroup memory: operands are loaded straight into fragments, each 64x128 tile is computed by 2x4 simdgroups, threadgroups are swizzled, one barrier per 256 K. Not unrolling the K loop is what makes it fast (0% -> 15%). When K >= 3*max(M, N), K is split into 4096-wide partitions dispatched one after another and accumulated into dst, so that the operand slices stay in the cache (MLX does the same for long K).

**A4: GDN with 4 lanes per row** (`kernels/gated_delta_net.metal`, `ggml-metal-ops.cpp`). With 32 lanes per state row, the recurrence was instruction bound (two 5-step reductions per token). With 4 lanes per row (8 for state size 256, otherwise each lane would need 64 registers) each lane holds 32 state values and a reduction takes 2 steps (8 lanes: 1.87x, 4 lanes: 1.98x). Other shapes, non-scalar gates and unaligned inputs keep the existing kernel.

**I8: int8 mat-mat** (`kernels/mul_mm.metal`: `kernel_mul_mm_q8a_f32`, `kernel_mul_mm_dq_<type>_i8`, `kernel_mul_mm_nax_i8`). Activations and dequantized weights are quantized to symmetric int8 with one scale per (row, 128 columns); before quantizing, each group of 128 values goes through an unnormalized Walsh-Hadamard transform (`i8_wht128`, 4 values in each of 32 lanes, 2 in-lane add/subtract stages + 5 `simd_shuffle_xor` stages). Both sides use the same transform, so the dot product is kept (the 1/128 is folded into the activation scale), while outliers are spread over the group instead of inflating its scale. `matmul2d<int8, int8, int32>` accumulates a 128-wide group of K, which is then folded into the f32 accumulators (`c += s_a*s_w*ci`). Same tiling and split-K as A3; it reuses the buffer reserved by A3 and needs no extra memory. One scale per 32 columns is also more accurate, but folds 4x as often and makes Qwen pp2048 25% slower, so the groups stay at 128 columns and the transform recovers the accuracy: KL divergence Qwen 0.0023 -> 0.0007, Llama 0.0009 -> 0.0004, gemma 0.112 -> 0.067, at a speed cost of 0-2%. This is the same kind of lossy shortcut as the q8_1 activations of the CUDA MMQ path and oMLX's oq_a8 (accuracy in section 10).

**A5: SWIGLU -> down projection** (`ggml-metal-fusion.cpp`, `kernels/unary.metal`). When the output of SWIGLU feeds a NAX mat-mat, the GLU kernel writes the f16 or int8 activations (with scales) that mat-mat needs directly; the f32 GLU output and the separate conversion pass are gone. Results are bit-identical to the unfused path.

**S1: keep the conversation cache when thinking is turned off** (`tools/ui`). The interface's thinking levels low / medium / high were already sent as `thinking_budget_tokens` and switching between them keeps the cache; only "off" sent `chat_template_kwargs.enable_thinking=false`, which makes the Qwen3.8 template drop a paragraph at the start of the system part, so the whole conversation was processed again from about the 5th token. "Off" now sends `thinking_budget_tokens: 0`, which gives the same output as the template's empty thinking block with an unchanged prompt prefix. A new setting "Keep the conversation cache when thinking is off" (Settings -> Developer, on by default).

**S2-a: no zero-fill at load** (`ggml-metal-device.cpp`, `common/common.cpp`). Metal shared buffers come from `vm_allocate` and are already zero, but the KV cache was cleared once after allocation and again after warm-up, touching and committing every page (about 16 GiB of KV and 2.4 GiB of recurrent state at 262k context). The Metal side records whether a buffer has been touched since allocation and skips the clear if not; the `common` side only resets the KV cells after warm-up instead of wiping the data.

**K3: cross-row mat-vec for 2-3 rows** (`kernels/mul_mv.metal`). Same lane layout as the single-row mat-vec, but the quants and scales of a block are unpacked once and dotted with the 2-3 activation rows; the unpacked values are kept in half to limit register use. q4_K for 2-3 rows, q5_K for 2 rows.

**S2-c: first residency request in the background** (`ggml-metal-device.cpp`). The first `requestResidency` of a residency set maps every page for the GPU, about 0.4 s for the KV of a 262k context. For shared buffers untouched since allocation the request runs on a background queue, after which the set joins the keep-alive set; freeing the buffer waits for it.

**A2 gate** (`ggml-metal-ops.cpp`). A2 converts the f32 activations to f16 before the tensor mul_mm, one more dispatch with two barriers per mul_mm, a fixed cost; below 128 rows it costs more than half activations save, and so it does at 128-512 rows for small products (K/V projections, the small recurrent-state projections; gpt-oss pp128 -7%, Llama Q8_0 -10%). The conversion now starts at 128 rows and 4 GFLOP per product (the NAX mat-mat takes f16 only and still converts), and the extra buffer is reserved under the same condition. Thresholds of 2 / 4 / 8 / 16 GFLOP were swept: 4 is the only one that is not slower on any of the four models at pp128 / 256 / 512.

**H3: GQA-packed NAX attention** (`kernels/fa_tensor.metal`: `kernel_flash_attn_ext_nax_gqa`; `ggml-metal-ops.cpp`). In decode and speculative verify the vec kernel reads K/V once per query head. The new kernel packs the G query heads that share a KV head and the ne01 tokens into the rows of one NAX tile (p = g*ne01 + i), so each K/V block is read once; the KV range is split over 32 threadgroups whose results are written in the temp-buffer layout of the vec kernels and combined by the existing `kernel_flash_attn_ext_vec_reduce`; the first threadgroup also folds the sink into its partial result (as the vec kernel does). Up to 16 packed rows use one group of simdgroups, up to 32 two. Conditions: head size 64-512, F16 K/V, a mask, no ALiBi / softcap, at least 2 query heads per KV head; with fewer than 5 packed rows (single-token decode with 4 query heads per KV head) and KV shorter than 16k, most of the tile would be empty rows and the vec kernel stays.

**H4: NAX few-row mat-mat for 2-64 rows** (`kernels/mul_mm.metal`: `kernel_mul_mv_nax_f32`; `ggml-metal-common.cpp`, `ggml-metal-ops.cpp`). The src1 rows are the M = 16 rows of a 16x32x16 matmul2d (one or two 16-row tiles per pass, more rows as further passes along the second grid dimension), the 32 weight rows its N; each lane dequantizes 16 weights straight into a half fragment through the dequantize function of the format, without threadgroup memory; 4 simdgroups split K and are summed in threadgroup memory at the end. So that each lane dequantizes a whole 16-weight group at once (the unit of the dequantize functions), K is permuted within each 64-weight chunk, identically for src0 and src1. q5_K has its own dequantize function with 16-byte loads and bit operations instead of per-weight branches. One function decides which row counts are enabled for each format (section 7.1). The residual ADD fuses into its store (MUL_MAT + ADD).

**M1: MoE mat-mat from 16 tokens** (`ggml-metal-common.cpp`). `ggml_metal_op_mul_mat_id_use_mm` lowers the threshold from 32 to 16 on devices with tensor units; others keep 32.

**M2: MoE mat-mat tiles of 64 entries** (`kernels/mul_mm.metal`: `kernel_mul_mm_id_map0`, `kernel_mul_mm_id`; `ggml-metal-device.cpp`, `ggml-metal-ops.cpp`). The routing prepass cuts the entries of each expert into tiles, and the main kernel dequantizes 64 weight rows once per tile and multiplies them with the entries of the tile. A function constant switches the tile size from 32 to 64 in the prepass and the kernel together: a tile of 64 entries is multiplied in quarters of 16 rows with `matmul2d`, and quarters without entries are skipped; each thread loads one more activation row; threadgroup memory grows from 8 KB to 16 KB. Used only on devices with tensor units and when the experts get at least 128 entries on average.

**A1-BF16: BF16 KV cache** (`kernels/fa_tensor.metal`, `ggml-metal-ops.cpp`). The kernels of A1 and H3 are templates over the K/V element type: a BF16 cache is read as is and each element converted to f16 in registers (clamped to the f16 range), so Q, K, V and P stay f16 in the MMA. Before, a BF16 cache always took upstream's tensor kernel.

**A3-BF16: BF16 weights** (`kernels/mul_mm.metal`, `ggml-metal-ops.cpp`). From 1024 rows, BF16 weights are converted to f16 once per mat-mat like the other formats (into the same extra buffer as the dequantized quantized weights) and multiplied with f16 activations; the int8 variant is not used for them. Below 1024 rows BF16 keeps upstream's f32-activation path.

**A1-MLA: MLA head sizes** (`kernels/fa_tensor.metal`, `ggml-metal-ops.cpp`). The prefill kernel splits the K and V head dims separately, so that it covers 192/128 of DeepSeek / GLM / Kimi style models and 576/512 with V a view of K (head dim split over 1 and 4 simdgroups). H3 stays at equal K and V head sizes.

**F4: NVFP4 and TQ1_0 weights** (`kernels/dequantize.h`, `kernels/mul_mv.metal`, `kernels/mul_mm.metal`, `ggml-metal-device.cpp` and 7 more files). Both formats now take every Metal path the other formats take: mat-vec (a dedicated kernel each; NVFP4 also the 2-5 row kernel), the few-row MMA, mat-mat, MoE mat-mat, and on M5 the NAX paths through `NAX_QTYPES` (A3, I8, H4). NVFP4 decodes its UE4M3 sub-block scales in the kernel (0x7F, the NaN code, decodes to 0 as on the CPU) with the E2M1 table of mxfp4; TQ1_0 extracts its base-3 digits as the CPU reference does.

**H3-Q: quantized KV caches** (`kernels/fa_tensor.metal`, `ggml-metal-device.cpp`, `ggml-metal-ops.cpp`). The H3 kernel is instantiated per block type of the cache (q4_0 / q4_1 / q5_0 / q5_1 / q8_0 / iq4_nl), addresses each row in bytes and dequantizes 4 values per load in registers with the existing `dequantize_*_t4`; the kernel name carries the cache type. With at most 4 packed rows the vec kernel is faster at any length and stays; the conditions for F16 / BF16 are unchanged. At larger batches upstream first converts a quantized cache to F16 for the other kernels, which is unchanged.

## 11. Remaining gaps

1. **MoE prefill.** gpt-oss with 8k / 30k prompts is 6% / 9% slower than oMLX, gemma 3% / 5%. In the time breakdown before M2, about 69% of gpt-oss prefill was MUL_MAT_ID at about 26 TFLOP/s, against about 52 TFLOP/s for the dense NAX mat-mat; M2 made gpt-oss prefill 24-37% faster, but the per-expert mat-mat is still clearly below the dense path. The next step is a register-resident NAX kernel like A3 for the per-expert mat-mat (the H5 few-row approach is slower at large batches, see section 9).
2. **Qwen MTP.** At 8k, oMLX decodes with MTP at 57.5 t/s against 42.7 here (43.7 vs 40.8 at 30k); without speculative decoding the two are only 2-5% apart, so the gap is mostly in the speculative layer (draft length, acceptance, the cost of the draft head itself). This project changed only the Metal backend and did not break that down.
3. **Decode bandwidth.** Short-context decode is on par with upstream but still short of the bandwidth limit: Qwen 2k decode 26.0 t/s x 19.5 GB ≈ 507 GB/s, Llama Q4_K_M 95 t/s x 4.9 GB ≈ 467 GB/s, i.e. 83% / 76% of the nominal 614 GB/s. oMLX is 2-5% faster on Qwen.
4. **Two slowdowns with a BF16 KV cache.** gemma prefill is about 5% slower than upstream's BF16 tensor kernel; Llama-3.1-8B decode at 32k is 14% slower (4 query heads per KV head, only 4 packed rows, the same case the H3-Q threshold excludes, and it should fall back to the vec kernel by row count in the same way). The gemma case needs another measurement by head size (its global layers have 512). For now `GGML_METAL_FA_NAX_BF16_DISABLE=1` switches the whole change off.
5. **Attention at medium batches (in progress, not in the commit list above).** The H3 tile holds at most 32 packed rows; beyond that the vec kernel (fewer than 20 queries per head) or A1 takes over, and steps of 9-64 tokens at long context are furthest from the limit. The change in progress grows the tile to 64 / 128 rows, dispatches blocks of rows, splits the KV range into fewer parts above 32 queries per head, and lets quantized caches at larger batches skip the F16 conversion. Prototype results (F16 cache, @32k, new / now, t/s): Llama-3.1-8B steps of 16 tokens 515 / 236, 32 tokens 744 / 351; gemma 12 tokens 469 / 268, 32 tokens 780 / 548; gpt-oss 16 tokens 631 / 382, 32 tokens 931 / 634; q8_0 cache with 32 tokens (Llama) 500 / 302. The boundary between the packed kernel and A1 is still being measured: on Llama packing is faster up to 128 queries per head and slower at 256.
6. **The ops furthest from the hardware limit (roofline).** With the ideal time estimated as max(FLOP / 60 TFLOP/s, bytes / 560 GB/s) (measured before H3-Q): attention with 16 queries per head reaches only 0.02-0.15 (the item above), small-batch decode with a quantized KV cache 0.01-0.35 (partly improved by H3-Q), MLA 576 decode 0.01-0.14, MoE mat-mat at large batches 0.35-0.6 (item 1), the dense mat-vec at 2-8 and 32-64 rows about half of ideal, F16 attention prefill 0.6-0.84.
7. **I8 accuracy.** On gemma, I8 brings the KL divergence to about 3x the reference of upstream's `-fa on`/`-fa off` (section 10). Finer groups are too slow (one scale per 32 columns: Qwen -25%), the Walsh-Hadamard transform recovered part of it; a full fix needs a way to tell per matrix how the activations are distributed, for now it can only be switched off as a whole.
